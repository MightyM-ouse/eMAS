## Central decisions B-1 through B-7

### B-1 — fixed CEC projection table

**ACCEPT for bounded T4.**

Use:

`CEC-FIELD-PROJECTION/1`

as a fixed, versioned engine compatibility table.

The `XmlId -> XmlDocuments.XmlKind` join is acceptable because it uses factual content already present in the immutable ScannerObservations document and does not reopen source files or reparse XML.

This is a bounded compatibility decision, not a permanent claim that all future CEC fields must be hard-coded. Before T1b/T2 materially expand the evidence field catalogue, revisit whether selector metadata should become governed schema/workbook content.

B-1 is closed.

### B-2 — runtime evidence-strength cap

**ACCEPT.**

A fired rule's declared evidence strength is a ceiling, not permission to overstate weaker evidence observed at runtime.

Therefore hit strength is:

`min(declared output strength, weakest cited normalized evidence strength)`

in ordinal terms.

Keep `StrengthCappedByEvidence`.

This is defence in depth alongside the T3a authoring-time `maxEvidenceStrength` guard and does not mutate the CEC fact.

B-2 is closed.

### B-3 — ReviewRequired for NotAssessed

**ACCEPT `ReviewRequired = true`.**

For Pre-Sales, `NotAssessed` means the consultant lacks enough evidence/capability/configuration to make the identification conclusion. It must remain visible for clarification rather than silently look complete.

This applies to:

- unavailable required evidence;
- capability not collected;
- no Identification rule configured for a configured dimension.

B-3 is closed.

### B-4 — physical-only v4 at MEDIUM

**ACCEPT the oracle's generic engine behavior, with an explicit governance boundary.**

If a validated Runtime JSON deliberately contains an **Effective** Identification rule whose physical v4 marker produces a MEDIUM hit, the generic engine may return:

- `EvaluationStatus = Evaluated`;
- the configured v4 TechnicalStandard value;
- policy-derived MEDIUM-tier confidence;
- `ReviewRequired = true`.

This does **not** authorize the production R-FMT-02 legacy intent to become Effective now.

Production governance remains:

- physical v4 evidence is capped at MEDIUM;
- physical evidence alone can never produce STRONG/HIGH v4 identification;
- R-FMT-02 remains RE_MODEL / source-refresh controlled;
- Strong/reliable v4 structured identification requires T2 `SubmissionUnitXmlInventory`;
- no production v4 rule becomes Effective merely because the generic engine supports MEDIUM semantics.

This avoids hard-coding `eCTD_4_0` business meaning into the shared engine while preserving the accepted configuration-driven architecture.

B-4 is closed.

### B-5 — lower-tier contradiction confidence

**ACCEPT: no automatic confidence rewrite in Identification/1.0.**

When a selected candidate has a contradiction below the winning tier but at/above the configured floor:

- retain the selected value;
- add `LowerTierContradiction`;
- set `ReviewRequired = true`;
- leave Confidence determined by the explicit configured Identification confidence policy.

The current confidence-policy model has no governed contradiction-downgrade axis. Hard-coding one now would bypass T3a/T3b governance.

A future explicit contradiction-confidence policy may extend this behavior.

B-5 is closed.

### B-6 — UNKNOWN vs MANUAL_REVIEW tieBehavior

Both produce:

- null Value/ValueSet;
- `Confidence = UNKNOWN`;

`tieBehavior` may still inform later display/consultant wording, but it does not create a second executable status vocabulary.

B-6 is closed.
